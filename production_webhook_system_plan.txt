GLS production update plan

Goal
- Change the app from "manual local tester sends document data" to "monday webhook triggers file generation".
- monday becomes the source of truth for row data.
- The backend decides the document type from the webhook board ID.
- The backend fetches the row values from monday, generates the file, uploads it back to monday, and updates status columns.

Main production flow
1. monday sends a webhook to our backend when the status column changes.
2. Backend verifies and parses the webhook payload.
3. Backend reads board_id and pulseId/item_id from the webhook event.
4. Backend finds the board configuration from a local JSON config file.
5. Backend fetches the full monday row data for that item only.
6. Backend converts monday column values into document variables using the board configuration.
7. Backend applies defaults and derived values.
8. Backend generates the file using the configured template and output format.
9. Backend uploads the generated file to the correct monday Files column for that board.
10. Backend updates the monday status/result columns.
11. Backend returns success to monday.

Recommended endpoint design
- Keep the current generation code, but add a new production endpoint:
  POST /webhooks/monday/file-generator
- This endpoint will be the main production entrypoint.
- Keep /generate-document only for development/testing.
- Keep local_tester.html only as a dev tool, not as part of the production workflow.

Important monday webhook behavior
- monday first sends a JSON "challenge" when a webhook URL is created.
- The endpoint must return the same challenge JSON body.
- monday webhook payloads also include triggerUuid and isRetry.
- We should use triggerUuid as the idempotency key so we do not generate duplicate files on retries.

Production board routing design
- Create one editable JSON config file, for example:
  board_document_config.json
- Each board_id maps to one document setup.
- This makes the system easy to update without changing Python logic every time.
- The config should stay simple and clean so it can be updated by hand later.

Config rules
- Keep the JSON flat and human-readable.
- Put one board per block.
- Use the same names in both places:
  - monday column name
  - template variable / .docx placeholder
- That means a monday column named issuer_company_name matches {{ issuer_company_name }} automatically.
- Put fixed fallback values under defaults.
- Put only special exceptions under overrides.
- Put monday upload/status settings in their own small sections.
- For this design, the visible monday column names should stay stable and machine-friendly.
- Recommended style for column names:
  - issuer_company_name
  - bond_number
  - payment_deadline
- If needed, we can also keep a human-readable note field in the config for easier maintenance.
- Status labels are safer if stored by index as well as text.

How file type is decided
- board_id from the webhook decides everything:
  - document_type / template_type
  - output_format
  - file_name_template
  - column-name matching mode
  - optional overrides
  - defaults
  - upload file column
  - success/error status update behavior

How monday data is fetched
- Use the webhook event values:
  - boardId
  - pulseId
- Then query monday for that single item's current column values.
- Do not fetch all board rows.
- For speed, only load the changed row identified by pulseId/item_id.
- Fetch:
  - item id
  - item name
  - board id
  - column_values.id
  - column_values.text
  - column_values.value
  - column_values.type
  - column.title
- After that, build one normalized row dictionary in Python.
- This means "full row data" only for that one target item, not the whole board.

Recommended internal normalization flow
1. Load raw monday row data.
2. Convert row data into a simple dictionary by column name.
3. Match monday column names directly to template variable names.
4. Apply overrides only for special cases where names do not match.
5. Apply defaults from config if a value is empty.
6. Apply existing derived alias logic if still useful.
7. Generate the final template context.

Document generation rules
- PDF:
  - keep the current HTML -> PDF flow
- DOCX:
  - use the .docx template for that template_type
- The backend should not accept free-form template variables from the browser in production.
- In production, variables should come from monday row data and board config only.
- If a new field is added later, and the monday column name matches the template variable name, it should work without backend code changes.

What should change in current code
- Keep:
  - template rendering logic
  - monday auth/request helpers
  - upload-to-monday helper
  - PDF and DOCX generation logic
- Add:
  - webhook endpoint
  - board config loader
  - row fetch by item_id
  - monday row -> template context mapper
  - status update helper
  - idempotency protection using triggerUuid
- Reduce or isolate from production:
  - local_tester.html
  - /config/defaults
  - /templates
  - manual payload extraction flow from browser form data

Recommended backend steps in the new webhook endpoint
1. If request body contains challenge, return it immediately.
2. Validate request shape.
3. Read event.boardId and event.pulseId.
4. Find board config.
5. If triggerUuid was already processed, return success without regenerating.
6. Optionally update monday status to "Generating".
7. Fetch the full row from monday for that one item only.
8. Map monday values by matching column names to template variable names.
9. Apply overrides and defaults from board_document_config.json.
10. Generate file.
11. Upload file to the board's configured Files column.
12. Update monday status to "Set file" or another success label.
13. If anything fails, update monday status to "Error" and optionally save the error message in a text column.

Recommended extra config fields
- result_message_column_id
  - optional text/long_text column for success or failure notes
- document_name_template
  - custom file name template per board
- enabled
  - allow disabling one board without removing it
- Local file saving should stay disabled in production.
- The service should generate the file in memory and upload it directly to monday.

Recommended result/error behavior
- On success:
  - upload file
  - set status to success label
  - optionally write generated filename and timestamp to monday
- On error:
  - set status to error label
  - optionally write error details to a message column
- Do not silently fail.

About local tester and extra frontend logic
- local_tester.html is still useful for development.
- But production should not depend on the tester sending final document values.
- Production should depend on monday webhook + monday row fetch.
- So the tester should be treated as a dev-only utility, not the real business flow.

Recommended implementation order
1. Add board_document_config.json
2. Add monday webhook endpoint with challenge response
3. Add board config lookup by board_id
4. Add fetch-item-from-monday function
5. Add monday-row-to-template-context mapping
6. Add status update helper
7. Connect file generation and upload
8. Keep local tester for internal testing only

Small but important production notes
- Use triggerUuid for idempotency.
- Use stable monday column names for document variables.
- Do not save generated files locally in production.
- In Cloud Run, keep monday token in Secret Manager, not in JSON files.

Proposed final system design summary
- Input:
  monday webhook payload
- Router:
  board_id -> board_document_config.json
- Data source:
  monday row values fetched by pulseId/item_id
- Mapping:
  monday column names -> template variable names, plus optional overrides + defaults
- Renderer:
  PDF HTML template or DOCX template
- Output:
  generated file uploaded to monday Files column
- Result tracking:
  monday status column + optional message column

This is the cleanest direction for production because it removes manual data entry from the real flow and makes the board itself the source of truth.
